# Промпт: Реализация аутентификации и авторизации в Spring Security

```markdown
Ты — опытный Java / Spring Boot backend-разработчик и архитектор безопасности.

Мне необходимо реализовать «Задание 4. Аутентификация и авторизация в Spring Security» для моего существующего REST API приложения.

### Твоя задача:
Помоги мне пошагово спроектировать и написать код для выполнения всех требований задания с соблюдением best practices, принципов SOLID и стандартов безопасности Spring Security 6+ (Spring Boot 3+).

### ТРЕБОВАНИЯ К РЕАЛИЗАЦИИ

#### 1. Подключение и базовая конфигурация Spring Security
- Настроить `SecurityFilterChain` c поддержкой **HTTP Basic Authentication**.
- Настроить **CSRF-защиту** для запросов, изменяющих данные (POST, PUT, PATCH, DELETE).
- Реализовать endpoint/механизм для явного получения CSRF-токена клиентом (например, через `CookieCsrfTokenRepository.withHttpOnlyFalse()` или отдельный эндпоинт `/api/csrf`).
- Обеспечить бесконфликтную интеграцию безопасности с существующими REST-эндпоинтами и бизнес-логикой.

#### 2. Модель пользователей, регистрация и аутентификация
- **Хранение в БД:** Использовать JPA-сущность пользователя (`User` / `Account`), связанную с таблицей пользователей.
- **Безопасность паролей:** Хранить пароли исключительно в захэшированном виде с использованием `PasswordEncoder` (`BCryptPasswordEncoder`).
- **Регистрация (`/api/auth/register`):**
  - Валидация входных данных: проверка надёжности пароля (длина, спецсимволы/цифры) и уникальности имени пользователя/email (возвращать понятную ошибку при дубликатах).
  - Защита от эскалации привилегий: регистрация **никогда** не должна позволять клиенту передать роль администратора или повышенные права (по умолчанию назначается базовая роль, например `ROLE_USER`).
- **Состояние пользователя (User Details):**
  - Реализовать `UserDetailsService` и `UserDetails`.
  - Предусмотреть учёт статуса аккаунта (`isAccountNonLocked`, `isEnabled`, статус активности/блокировки в зависимости от бизнес-логики).

#### 3. Настройка авторизации и разграничение доступа
- **Роли и права:**
  - Реализовать минимум 2 роли (например, `ROLE_USER` и `ROLE_ADMIN` или предметные роли с разным набором привилегий/Granted Authorities).
- **Методы защиты:**
  - Включить `@EnableMethodSecurity`.
  - Защитить CRUD-эндпоинты и бизнес-операции комбинированно: на уровне URL (`securityMatcher`, `authorizeHttpRequests`) и с помощью аннотаций `@PreAuthorize` над сервисными методами/контроллерами.
- **Контекстная авторизация:**
  - Реализовать проверку владения ресурсом или контекстные ограничения (например: *пользователь может редактировать/просматривать только свои данные, а администратор — любые*):
    `@PreAuthorize("hasRole('ADMIN') or #username == authentication.name")` или через кастомный `SecurityExpression` / сервис проверки прав.
- Правила доступа должны строго согласовываться с ограничениями предметной бизнес-логики.

#### 4. Обработка ошибок безопасности (Exception Handling)
- Разграничить и корректно обрабатывать:
  - **401 Unauthorized:** Ошибки аутентификации (неверный логин/пароль, отсутствие токена) через кастомный `AuthenticationEntryPoint`.
  - **403 Forbidden:** Недостаточно прав / отказ в доступе через `AccessDeniedHandler`.
  - **400 / 422 / 409:** Нарушения бизнес-логики и правил валидации регистрации через `@ControllerAdvice` / `@RestControllerAdvice`.
- **Безопасность ответов:** Тело ошибки (JSON) не должно раскрывать чувствительные данные (stack trace, внутренние пароли, секреты базы данных). Формат ответа сделать унифицированным (со статусом, timestamp и читаемым сообщением).

#### 5. Коллекция запросов (Postman / HTTP Client)
- Подготовить структуру коллекции запросов (в формате `.http` файла для IntelliJ IDEA / VS Code или JSON для Postman):
  - Регистрация нового пользователя (валидные данные + сценарии с ненадёжным паролем / занятым логином).
  - Запрос на получение CSRF-токена.
  - Успешные запросы к защищённым бизнес-операциям от имени базового пользователя (с передачей Basic Auth и CSRF-заголовка `X-XSRF-TOKEN`).
  - Успешные запросы от имени пользователя с повышенными привилегиями (Admin/Manager).
  - Негативные сценарии:
    - 401 Unauthorized (без авторизации или неверный пароль);
    - 403 Forbidden (попытка обычного пользователя вызвать админский метод или действие над чужим ресурсом);
    - 403 Invalid CSRF token.
```
