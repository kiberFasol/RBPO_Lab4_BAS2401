# Лабораторная работа 4. Вариант 22 — Распределение мест в общежитии
## Аутентификация и авторизация в Spring Security

Проект представляет собой бэкенд-сервис для управления заселением в студенческое общежитие. В четвертой лабораторной работе реализована комплексная система безопасности на базе **Spring Security 6+ (Spring Boot 3+)**: аутентификация через HTTP Basic Auth, защита от межсайтовой подделки запросов (CSRF), ролевая модель доступа, контекстная авторизация (проверка владения ресурсом) и обработка исключений безопасности без утечки чувствительных данных.

- **Java 17**

## Архитектура безопасности (Лабораторная работа 4)

### 1. Аутентификация (HTTP Basic Authentication)
- Логином пользователя является его **`email`**.
- Пароли хранятся в БД исключительно в захэшированном виде с использованием `BCryptPasswordEncoder`.
- Реализованы интерфейсы `UserDetails` (`CustomUserDetails`) и `UserDetailsService` (`CustomUserDetailsService`).
- Учитываются статусы пользователя: флаги `enabled` (активность) и `account_non_locked` (блокировка). Попытка входа заблокированного пользователя отклоняется (401).

### 2. Регистрация пользователей (`POST /api/auth/register`)
- Доступна публично без предварительной аутентификации и без CSRF-токена.
- **Строгая валидация пароля:** длина от 8 до 64 символов, обязательное наличие минимум одной заглавной буквы, одной строчной буквы, одной цифры и специального символа (`@#$%^&+=!._-`).
- **Защита от эскалации привилегий:** регистрирующемуся пользователю принудительно и неизменяемо присваивается базовая роль `STUDENT`.
- Контроль дубликатов email с возвратом понятной ошибки **409 Conflict**.

### 3. CSRF-защита (Cross-Site Request Forgery)
- Все запросы, изменяющие состояние системы (`POST`, `PUT`, `PATCH`, `DELETE`), требуют передачи CSRF-токена (за исключением публичной регистрации).
- Используется `CookieCsrfTokenRepository.withHttpOnlyFalse()`, позволяющий клиентам считывать токен из cookie `XSRF-TOKEN` и передавать его в заголовке `X-XSRF-TOKEN`.
- Реализован отдельный публичный эндпоинт **`GET /api/csrf`** для явного получения токена клиентом.
- Недействительный или отсутствующий токен на изменяющих запросах отклоняется со статусом **403 Forbidden**.

### 4. Ролевая модель и разграничение доступа
В системе действуют 3 роли с четко разграниченным набором прав:

- **`ROLE_STUDENT` (Студент / Базовый пользователь):**
  - Просмотр каталога доступных комнат (`GET /api/rooms/**`).
  - Просмотр и редактирование **только собственного** профиля (`GET, PATCH /api/users/{id}`).
  - Подача заявлений на заселение **только от своего имени** (`POST /api/housing-applications`), а также просмотр, обновление и отзыв только своих заявлений (`GET, PATCH, DELETE /api/housing-applications/{id}`).
  - Просмотр **своего** договора найма (`GET /api/residence-contracts/{id}`).
  - Подача заявки на переселение **только по своему активному договору** (`POST /api/room-transfer-requests`), а также просмотр, редактирование и отмена только своих заявок (`GET, PATCH, DELETE /api/room-transfer-requests/{id}`).
  - *Запрещено:* просмотр списков чужих пользователей/договоров/заявок, создание/удаление пользователей и комнат, выполнение регламентных и служебных бизнес-операций.

- **`ROLE_STAFF` (Сотрудник общежития / Комендант):**
  - Все права на просмотр списков и детальной информации по любым пользователям, договорам, заявлениям и комнатам.
  - Изменение статуса и параметров комнат (`PATCH /api/rooms/{id}`).
  - Управление договорами найма (`POST, PATCH, DELETE /api/residence-contracts/**`).
  - Рассмотрение и управление любыми заявлениями на заселение и переселение.
  - Проведение бизнес-операций общежития (`/api/operations/**`): заселение студента (`/check-in`), одобрение переселения (`/transfers/{id}/approve`), досрочное расторжение договора (`/contracts/{id}/terminate`), закрытие истекших договоров (`/contracts/process-expirations`), перевод комнаты на ремонт (`/rooms/{id}/maintenance`).
  - *Запрещено:* создание новых учетных записей вручную в обход регистрации (`POST /api/users`), безвозвратное удаление учетных записей пользователей (`DELETE /api/users/{id}`), создание новых комнат (`POST /api/rooms`) и их физическое удаление (`DELETE /api/rooms/{id}`).

- **`ROLE_ADMIN` (Администратор системы):**
  - Полный (абсолютный) доступ ко всем возможностям системы без ограничений.
  - Создание пользователей с заданием произвольных ролей (`POST /api/users`) и их удаление (`DELETE /api/users/{id}`).
  - Добавление новых комнат в фонд общежития (`POST /api/rooms`) и удаление комнат (`DELETE /api/rooms/{id}`).
  - Доступ ко всем операциям персонала (`STAFF`) и любым пользовательским ресурсам.

Включена аннотация `@EnableMethodSecurity`. Настроена двухуровневая защита:
1. **На уровне URL (`SecurityFilterChain`):**
   - Публичные: `POST /api/auth/register`, `GET /api/csrf`.
   - Бизнес-операции (`/api/operations/**`): разрешены только `ADMIN` и `STAFF`.
   - Просмотр комнат (`GET /api/rooms/**`): доступен всем авторизованным пользователям.
   - Управление комнатами (`POST`, `PATCH`, `DELETE /api/rooms/**`): только `ADMIN` и `STAFF`.
2. **Контекстная авторизация (Method Security & SpEL):**
   - Реализован бин `SecurityService` (`@securityService`), выполняющий проверку владения ресурсом:
     - Студент может просматривать и редактировать только **свои** данные пользователя (`/api/users/{id}`).
     - Студент может создавать и просматривать только **свои** заявления на заселение (`HousingApplication`), договоры найма (`ResidenceContract`) и запросы на переселение (`RoomTransferRequest`).
     - Администраторы и персонал (`ADMIN` / `STAFF`) имеют полный доступ к любым объектам.

### 5. Обработка ошибок безопасности
Все ответы об ошибках унифицированы (`timestamp`, `status`, `error`, `message`, `path`) и не раскрывают stack trace или внутренние секреты:
- **401 Unauthorized:** Кастомный `RestAuthenticationEntryPoint` (отсутствие учетных данных, неверный пароль, заблокированный аккаунт).
- **403 Forbidden:** Кастомный `RestAccessDeniedHandler` (недостаточно прав роли, попытка доступа к чужому ресурсу или отсутствие/неверный CSRF-токен).
- **400 Bad Request:** Нарушения валидации полей DTO и некорректные параметры.
- **409 Conflict:** Попытка зарегистрировать дубликат email или нарушение бизнес-правил общежития.

## Запуск и тестирование

### 1. Подготовка базы данных
Выполните скрипт инициализации от суперпользователя postgres:
```bash
psql -U postgres -h localhost -p 5432 -f init-db.sql
```
Скрипт создаст базу данных `dormitory_db`, пользователя `dorm_app_user` с ограниченными DML-правами, структуру таблиц с колонками безопасности (`password`, `enabled`, `account_non_locked`) и тестовые записи с хэшами BCrypt.

### 2. Сборка и запуск тестов
```bash
mvn clean test
```
В проекте реализованы модульные и интеграционные тесты безопасности:
- `AuthControllerIntegrationTest` — тесты получения CSRF, регистрации с валидацией пароля и проверкой дубликатов;
- `OperationControllerIntegrationTest` — тесты проверки 401 при неавторизованном доступе, 403 при нехватке ролей, 403 при отсутствии CSRF-токена и успешных запросов от `ADMIN`.

### 3. Запуск приложения
```bash
mvn spring-boot:run
```
Сервер запустится по адресу: `http://localhost:8080`.

### 4. Тестирование эндпоинтов через `requests.http`
В корне проекта подготовлен файл **`requests.http`** (поддерживается в VS Code через расширение *REST Client* или встроенным HTTP-клиентом IntelliJ IDEA).

В файле настроены:
- Получение CSRF токена (`GET /api/csrf`) с автоматическим сохранением переменной;
- Регистрация нового студента (позитивный кейс, слабый пароль, дубликат email);
- Негативные тесты безопасности (401 без логина, 401 неверный пароль, 401 заблокированный аккаунт, 403 без CSRF, 403 попытка студента вызвать метод админа);
- Позитивные сценарии от студента (просмотр комнат, просмотр своего профиля, отказ 403 при попытке просмотреть чужой профиль, подача заявки на заселение);
- Позитивные сценарии от администратора (просмотр всех пользователей, добавление комнат, запуск бизнес-операций).
